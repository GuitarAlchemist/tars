# Program Synthesis and Library Learning: TARS's Promotion Staircase versus the Compression-Based Frontier

## Abstract

TARS's promotion staircase (Implementation → Helper → Builder → DslClause → GrammarRule) promotes patterns on recurrence counts plus eight boolean criteria, with Beta-Binomial weight updates and replicator dynamics for selection — but nowhere does a compression or minimum-description-length (MDL) objective enter any decision, and the "template" actually validated in the live pipeline is just the pattern's name string. This contrasts sharply with DreamCoder, Stitch, and LILO, whose abstraction step admits a library component only when it compresses the program corpus, and with FunSearch and AlphaEvolve, which mutate actual program text under an island-model population with automated evaluation — TARS's genetic algorithm instead evolves only an 8-float hyperparameter genome, and its replicator dynamics provides selection with no variation operator. Live state (`~/.tars`, read 2026-07-21) shows a 9-pattern population with a promotion-level desync between `recurrence.json` and `weights.json` and degenerate 1.0 success rates, confirming that the estimators are under-regularized and the population is far too small for island search today. Both proposed upgrades are concretely feasible: an MDL-scored abstraction step can be built by anti-unifying the RollbackExpansion corpus already stored in lineage records (Stitch-style), and an island model requires only k-sample variant generation in TraceCompiler (currently temperature 0.0) plus partitioning WeightedGrammar state. The decisive metrics are monotone decrease of corpus description length under library rewriting, and benchmark pass-rate on the existing 19-problem ProblemBank at fixed LLM-call budget versus the single-population baseline. All nine claims below survived adversarial review; none were flagged as unverifiable and none were refuted.

## Background

Two research programs define the current frontier of automated program synthesis with learned libraries.

The first is the **compression-based library learning** line. DreamCoder (Ellis et al., 2020; PLDI 2021) alternates a wake phase, which solves tasks by program search, with a sleep-abstraction phase in which "program components that best increase a Bayesian objective (intuitively, that best compress programs found during waking) are incorporated into the library." Stitch (Bowers et al., POPL 2023) made this abstraction step practical via corpus-guided top-down synthesis — syntactic pattern matching over intermediate abstractions that steers the search toward lambda abstractions maximally capturing shared structure across the entire corpus — running three to four orders of magnitude faster than DreamCoder's deductive compression. LILO (Grand et al., ICLR 2024) layers an LLM over Stitch to name and document abstractions (AutoDoc), and validates library quality by exactly two measures: corpus compression and downstream solve-rate. The unifying commitment: an abstraction earns its place in the library if and only if it makes the corpus shorter.

The second is the **LLM-as-mutation-operator** line. FunSearch (Romera-Paredes et al., Nature 2024) "searches for programs that describe how to solve a problem" by "pairing a pretrained LLM with a systematic evaluator," maintaining an island-model population: every reset period the m/2 islands whose best instances have the lowest score are discarded and reseeded by cloning best individuals from surviving islands, with best-shot prompting over k = 2 sampled parents. AlphaEvolve (Novikov et al., 2025) extends this to whole codebases, "improv[ing] an algorithm by making direct changes to the code." Here the unifying commitment is that variation operates on real program text and selection operates on real execution scores.

TARS occupies an adjacent but distinct design point. Its promotion pipeline (`v2/src/Tars.Evolution/PromotionPipeline.fs`) climbs patterns up a five-level staircase gated by recurrence counts and a governor scoring eight boolean criteria (`GrammarGovernor.fs`); its weighted grammar applies Beta-Binomial updates (`WeightedGrammar.fs`); its replicator dynamics redistributes selection mass across pattern species (`ReplicatorDynamics.fs`); and its evolutionary breeder runs a real-valued GA (`EvolutionaryPatternBreeder.fs`). The question this research unit answers is where TARS stands relative to the two frontier commitments — compression-gated abstraction and text-level variation under automated evaluation — and what, concretely, closes each gap. The findings below combine static code analysis of `v2/src/Tars.Evolution/` with live filesystem state read from `~/.tars/promotion/` on 2026-07-21, each claim independently confirmed by adversarial review.

## Findings

### 1. Promotion gates on recurrence, not compression

**Claim.** TARS promotes patterns purely on recurrence count and eight boolean criteria; no compression, utility, or MDL quantity enters any promotion decision, whereas DreamCoder's sleep-abstraction phase admits a library component only if it increases a Bayesian objective that compresses the corpus of wake-phase programs. (Confidence: high; confirmed twice under adversarial review.)

**Evidence.** The `classify` step gates solely on `record.OccurrenceCount < minOccurrences` (`v2/src/Tars.Evolution/PromotionPipeline.fs:153`–168). The one criterion that sounds like a complexity measure — `validateDeterministic`'s "RemovesComplexity" — is implemented as `candidate.PatternTemplate.Length > 0` (`PromotionPipeline.fs:202`), a non-emptiness check. `GrammarGovernor.evaluate` thresholds a 0–8 boolean score, approving at ≥ 6 and rejecting below 4 (`v2/src/Tars.Evolution/GrammarGovernor.fs:27`–52). A grep across `Tars.Evolution` finds no compression or MDL quantity in any promotion decision path. Review noted one minor imprecision that does not disturb the conclusion: roundtrip validation adds a semantic-match float gate (≥ 0.5) that can flip Approve to Reject, but that gate is a similarity check on identifiers, not a compression, utility, or MDL quantity; likewise `RoundtripValidation.quickValidate` includes a single-instance length-direction sanity check, a boolean penalty on one string pair rather than a corpus-level objective. By contrast, DreamCoder's library grows only when a component compresses the wake-phase program corpus under its Bayesian objective (Ellis et al., 2020).

### 2. The validated "template" is literally the pattern name

**Claim.** In the live pipeline run, the `PatternTemplate` that gets validated is the pattern's name string, not any template body — so RemovesComplexity is trivially true for every non-empty pattern name, and MDL scoring is currently impossible without re-plumbing. (Confidence: high; confirmed twice.)

**Evidence.** `PromotionPipeline.run` calls `propose candidate.Record.PatternName rollback` (`v2/src/Tars.Evolution/PromotionPipeline.fs:332`), and `propose` assigns its first argument to `PatternTemplate` (`PromotionPipeline.fs:189`–192) — hence `PatternTemplate := PatternName`. TraceCompiler does produce a real JSON WoT template (`v2/src/Tars.Evolution/TraceCompiler.fs:103`, 125–132), and review found that `RetroactionLoop.fs:410`–418 does thread that template into `TraceArtifact.PatternTemplate` before calling `run` — a refinement of the original evidence wording — but `run` then ignores the artifact's template field entirely: `inspect`/`extract` never read it, `classify` resets it to the empty string, and `propose` overwrites it with the name. The substantive conclusion holds either way: nothing resembling a template body reaches validation, so any compression-based score computed there would be measuring the length of a name.

### 3. A compression ratio is computed but dead

**Claim.** GrammarDistillation already computes a per-production `CompressionRatio` (trace tokens / production tokens), but the value never influences `SuggestedLevel`, `toWeightedRule`, or any promotion decision — TARS has a vestigial hook for exactly the MDL signal DreamCoder and Stitch make central. (Confidence: high; confirmed twice.)

**Evidence.** `CompressionRatio` is defined (`v2/src/Tars.Evolution/GrammarDistillation.fs:64`) and computed (`GrammarDistillation.fs:206`–209, 217), but `SuggestedLevel` derives only from success rate and trace counts (`GrammarDistillation.fs:218`–221, 245–248), and `toWeightedRule` reads only `SuccessRate`/`TraceCount` (`GrammarDistillation.fs:284`–296). One correction from review: the original grep assertion that `render()` was the sole other consumer is wrong — `GrammarMlBridge.fs` consumes `CompressionRatio` as an ML feature (lines 43, 127, 140, 153, 292) — but `GrammarMlBridge.evolveAsync` has zero callers anywhere in `v2/src` (only its fsproj entry and a test reference it), so it is itself dead code. The existence of a second, also-dead consumer if anything reinforces the vestigial-hook thesis: the signal that Stitch's top-down synthesis (Bowers et al., POPL 2023) optimizes end-to-end is computed in TARS and then discarded on every live path.

### 4. Abstraction is single-trace and exact-match; the frontier is corpus-guided anti-unification

**Claim.** TARS abstraction operates one trace at a time (a single LLM call) and merges productions only on exact SHA256 structural fingerprints, so near-duplicate traces never yield a shared abstraction — unlike Stitch's corpus-guided anti-unification, which finds lambda abstractions maximizing shared structure across an entire corpus and runs 3–4 orders of magnitude faster than DreamCoder's compression. (Confidence: high; confirmed twice.)

**Evidence.** `TraceCompiler.compileFromTrace` takes exactly one trace and one goal per call (`v2/src/Tars.Evolution/TraceCompiler.fs:27`–32) and issues a single `llm.CompleteAsync` call. `GrammarDistillation.fingerprint` is a SHA256 hash over the exact slot signature (`Kind:InputType->OutputType`, joined) plus the exact edge signature (`v2/src/Tars.Evolution/GrammarDistillation.fs:84`–89); any variation in node kind, inferred type, or edge order changes the hash. `distillAll` groups strictly by identical `Id` and merges only within groups (`GrammarDistillation.fs:264`–268). Two traces differing in a single inferred type therefore produce two distinct productions with no shared abstraction — precisely the case anti-unification exists to handle. Stitch's published characterization (corpus-guided top-down synthesis; 3–4 orders of magnitude speedup over DreamCoder's deductive library learning) and LILO's LLM-documented abstractions match the cited papers. The 22 RollbackExpansion strings observed live in `lineage.json` constitute a ready-made corpus for such a pass (see Finding 9).

### 5. The GA evolves hyperparameters, not programs

**Claim.** TARS's "evolutionary pattern breeder" evolves only an 8-dimensional real-valued hyperparameter genome (CoT/ReAct/ToT/GoT weights, step multiplier, temperature, confidence threshold, branching factor), never pattern or program structure — categorically weaker than FunSearch/AlphaEvolve, where the LLM is the mutation operator over actual program text and an automated evaluator scores each variant. (Confidence: high; confirmed twice.)

**Evidence.** `PatternGenome` is exactly eight floats (`v2/src/Tars.Evolution/EvolutionaryPatternBreeder.fs:15`–33, with `genomeDimension = 8`), mapped to and from arrays for a generic GA (`EvolutionaryPatternBreeder.fs:36`–51). Fitness is a retrospective prediction-penalty over stored `PatternOutcome` records — no candidate is ever executed (`EvolutionaryPatternBreeder.fs:66`–101). Even the uncalled `GrammarMlBridge` breeding path evolves 10-dimensional feature vectors, never program text. FunSearch, by contrast, pairs a pretrained LLM with a systematic evaluator over program text (Romera-Paredes et al., 2024), and AlphaEvolve makes direct changes to code (Novikov et al., 2025). Notably, TARS already possesses the missing evaluator: ProblemBank's curated F# problems with compile-and-validate gates (`v2/src/Tars.Evolution/ProblemBank.fs:182`–205).

### 6. An island model is implementable but blocked by population size and zero temperature

**Claim.** A FunSearch-style island model (m islands, worst m/2 discarded each reset period, survivors cloned to reseed, best-shot prompting with k = 2 sampled parents) is directly implementable over TARS's WeightedGrammar state, but is currently blocked by two facts: the live pattern population is only 9 recurrence records / 8 weighted rules, and TraceCompiler samples deterministically at temperature 0.0, so no variant diversity is ever generated. (Confidence: high; confirmed twice, including live-state reads.)

**Evidence.** Live state read 2026-07-21: `~/.tars/promotion/recurrence.json` contains exactly 9 patterns; `weights.json` contains exactly 8 rules. The TraceCompiler request sets `Temperature = Some 0.0` (`v2/src/Tars.Evolution/TraceCompiler.fs:75`), producing one deterministic abstraction per trace. The structural substrate for islands exists: weighted selection at `v2/src/Tars.Evolution/WeightedGrammar.fs:150` and the recurrence store at `v2/src/Tars.Evolution/PromotionPipeline.fs:18`. The FunSearch Methods-section details were verified nearly verbatim: every 4 hours programs from the m/2 lowest-scoring islands are discarded, empty islands are reseeded by cloning one of the best individuals from a surviving island, and k = 2 because "two functions lead to better results compared to just one." Review notes that "directly implementable" is a design judgment, but the factual scaffolding is exactly as claimed.

### 7. Live defect: promotion levels desynchronized between stores

**Claim.** The live weight store disagrees with the recurrence store about promotion levels: five `ga.*` patterns are at GrammarRule in `recurrence.json` but "implementation" in `weights.json`, because `WeightedGrammar.updateWeight` never touches `Level` and `PromotionPipeline.persist` updates only the recurrence store — so any level-aware selection (`normalizeByLevel`, replicator species) operates on stale levels. (Confidence: high; confirmed twice against live data.)

**Evidence.** Observed 2026-07-21: `recurrence.json` has `ga.routing_fallback_cascade`, `ga.domain_skill_fastpath`, `ga.orchestrator_pipeline`, `ga.hook_lifecycle_fsm`, and `ga.confidence_evidence_response` all at `{"Case":"GrammarRule"}`, while `weights.json` lists the same five at Level `"implementation"`. The mechanism is fully explained in code: `updateWeight` copies the rule changing only `SuccessRate`/`Confidence`/`SelectionCount`/`LastUpdated`, leaving `Level` untouched (`v2/src/Tars.Evolution/WeightedGrammar.fs:136`–147); `persist`'s Approve branch updates `CurrentLevel` only in the recurrence store (`v2/src/Tars.Evolution/PromotionPipeline.fs:254`–263); `run`'s `WeightedGrammar.save` (at `PromotionPipeline.fs:375`) writes the stale rules back to disk; and `normalizeByLevel` groups by the stale `Level` (`WeightedGrammar.fs:168`–174). New weight entries receive correct levels only at creation (`fromRecurrenceRecords`), so existing rules drift exactly as observed. This is a real live defect and a prerequisite fix for any level-stratified evolution.

### 8. Replicator dynamics has selection but no variation

**Claim.** ReplicatorDynamics gives TARS selection pressure (dx_i/dt = x_i(f_i − f_avg), pruning below threshold) but no birth or variation operator, so the grammar ecosystem can only redistribute mass among and prune the existing 9 species — it is mathematically incapable of discovering new patterns, violating the variation-plus-selection minimum for evolutionary search that grammar-based genetic programming formalizes via grammar-constrained mutation and crossover operators. (Confidence: high; confirmed.)

**Evidence.** `ReplicatorDynamics.step` implements pure proportion redistribution — x_i(t+1) = x_i + dt · x_i · (f_i − f_avg), with floor and renormalization (`v2/src/Tars.Evolution/ReplicatorDynamics.fs:110`–127) — with `PruneThreshold = 0.001` and `SmoothingFloor = 0.01` in the default configuration (`ReplicatorDynamics.fs:48`–53). No function in the module creates new species; `buildSpecies` only wraps existing WeightedRules, so the ecosystem can never exceed its initial species set. The grammar-based GP literature (McKay et al., 2010; O'Neill & Ryan, 2001) defines evolutionary search as grammar-constrained variation — genotype-to-phenotype mapping through BNF productions — plus selection. TARS has the grammar (EBNF in `grammars/`, the WoT DSL) and the selection, but not the variation.

### 9. The MDL success metric is computable today from existing telemetry

**Claim.** An end-to-end MDL success metric requires no new telemetry: lineage records already persist RollbackExpansion strings (the pre-abstraction corpus) alongside each promoted pattern, so "total description length of the trace corpus rewritten with the current library" is computable from `~/.tars/promotion/lineage.json` today. The decisive experiment is whether that quantity decreases monotonically across evolve cycles while ProblemBank pass-rate at fixed LLM-call budget does not regress. (Confidence: medium; confirmed with caveats consistent with that confidence level.)

**Evidence.** `persist` stores `RollbackExpansion` in every `LineageRecord` (`v2/src/Tars.Evolution/PromotionPipeline.fs:245`); TraceCompiler builds it as a step-by-step expansion of the trace (`v2/src/Tars.Evolution/TraceCompiler.fs:107`–123). Live 2026-07-21: `lineage.json` is 33,234 bytes containing 23 records, of which 22 carry non-null RollbackExpansion strings (coverage is near-total rather than literally universal — one record lacks it); `~/.tars/pattern_outcomes.json` holds exactly 231 outcome records; and ProblemBank exposes `all`/`byDifficulty`/`summary` over the curated 19-problem suite (`v2/src/Tars.Evolution/ProblemBank.fs:182`–205, anchor `ProblemBank.fs:200`). Two review caveats: because live templates are just names (Finding 2), the description length of "the corpus rewritten with the current library" is only crudely computable today — name-for-expansion substitution plus definition length — and the proposed experiment design is a judgment, not a code fact. But the corpus itself is persisted, so the core assertion stands: no new telemetry is required, and the success criterion is falsifiable. This is exactly how DreamCoder and LILO validate library quality — corpus compression plus downstream solve-rate, with LILO reporting that it "solves more complex tasks and learns richer libraries" than DreamCoder on three synthesis benchmarks.

### Related finding: under-regularized estimators (prerequisite for any fitness comparison)

**Claim.** Two statistical estimators feeding promotion are biased: `extract` collapses a pattern's entire score history into a single pseudo-sample when averaging (a pattern with 100 prior observations weighs the same as one new artifact), and `bayesianUpdate` with `SelectionCount = 0` yields a posterior rate of exactly 1.0 or 0.0 after one observation because the configured `PriorSuccessRate` pseudocounts are never injected — visible in live data as five rules pinned at SuccessRate exactly 1.0. (Confidence: high; confirmed twice, including re-derivation of the update math.)

**Evidence.** `PromotionPipeline.fs:135`–136 computes `let allScores = existing.AverageScore :: (group |> List.map (fun a -> a.Score))` followed by `List.average` — the prior mean counts as one element regardless of `OccurrenceCount`, a mathematically biased running mean. In `WeightedGrammar.fs:100`–106, `effectiveCount = float priorCount * decayFactor` equals 0 on first update, so a single success gives alpha = 1, beta = 0, and a posterior of exactly 1.0 (0.0 on failure), which stays saturated for all-success histories. `defaultConfig.PriorSuccessRate = 0.5` is defined (`WeightedGrammar.fs:59`, 66) but grep confirms it is referenced nowhere else in `src` — `bayesianUpdate` is called with `rule.SuccessRate`/`SelectionCount` only (`v2/src/Tars.Evolution/WeightedGrammar.fs:141`–142). Live confirmation: all five `ga.*` rules in `weights.json` show SuccessRate exactly 1 at SelectionCount 4. Saturated fitness destroys selection gradients, so this must be fixed before any island fitness comparison is meaningful.

No claims were flagged as unverifiable. Every claim in this document was confirmed by adversarial review against code anchors, live filesystem state, or published sources. ## Opportunities for TARS

Ranked by leverage per unit of effort, with prerequisites ordered first.

1. **Fix the template plumbing (prerequisite, near one-line).** Thread the real WoT template through `PromotionPipeline.run`: pass the record's stored template rather than `candidate.Record.PatternName` at `PromotionPipeline.fs:332`. RetroactionLoop already places TraceCompiler's JSON template on the artifact; `run` just has to stop discarding it. Nothing compression-based is possible until validation sees a template body (Finding 2).

2. **Fix the level desync (prerequisite, small).** On Approve, rewrite the matching WeightedRule's `Level` in the weights list before `WeightedGrammar.save` (`PromotionPipeline.fs:375`). This must land before any island or level-stratified evolution, or islands will be stratified on wrong data (Finding 7).

3. **Regularize the estimators (prerequisite, small).** Weight the prior mean by `OccurrenceCount` in `extract`, and seed `bayesianUpdate` with fixed pseudocounts (alpha0 = beta0 = 1, i.e., Laplace smoothing) so rates cannot saturate at 0 or 1. Saturated fitness destroys the selection gradients every downstream evolutionary mechanism depends on.

4. **Make compression a first-class promotion force (medium).** Insert an MDL scoring step between EXTRACT and CLASSIFY: score each candidate by ΔDL = DL(corpus without abstraction) − (DL(corpus with abstraction) + DL(abstraction definition)), and replace the trivial RemovesComplexity boolean with ΔDL > 0. Feed the already-computed `CompressionRatio` into `SuggestedLevel` and `WeightedRule.RawScore` so the dead signal (Finding 3) starts doing work.

5. **Add a corpus-level anti-unification pass (medium).** Relax GrammarDistillation's exact SHA256 fingerprint to allow typed-slot variables, anti-unify across distilled productions, and use LILO-style AutoDoc via the existing LLM to name each abstraction. The 22 RollbackExpansion strings in `lineage.json` are the ready-made corpus (Findings 4, 9).

6. **Upgrade breeding to operate on program text (larger).** LLM-mutate WoT template JSON with best-shot prompting over k = 2 parents (FunSearch-style), evaluate on ProblemBank via the existing BenchmarkRunner compile-and-validate gates, and feed scores back as fitness — replacing the 8-float hyperparameter genome as the object of evolution (Finding 5).

7. **Grow the population, then partition into islands (larger, two phases).** Phase 1: sample n > 1 abstractions per trace at temperature ≈ 0.8 in TraceCompiler (currently `Some 0.0`) to grow the population past ~50. Phase 2: add an `Island` field to `WeightedRule`, run evolve cycles per island, cull and reseed the worst m/2 on a cycle cadence, and cluster by score-signature on ProblemBank subsets to preserve diversity (Finding 6).

8. **Close the variation loop in replicator dynamics (larger).** When replicator dynamics prunes a species, trigger an LLM-mutation birth event: mutate a high-fitness survivor's WoT template under the WoT EBNF grammar via the existing constrained-decoding path (`ConstrainedDecoding.fs`) so offspring are syntactically valid by construction — grammatical evolution with the LLM as the mutation distribution (Finding 8).

9. **Instrument the decisive experiment (`tars promote mdl`).** Report DL(corpus | library) in tokens per evolve cycle. Success criterion for the abstraction upgrade: DL strictly decreases over 5 consecutive cycles AND ProblemBank pass-rate is non-decreasing at fixed LLM-call budget. For the island upgrade: best-island benchmark score beats the single-population baseline at equal total LLM calls (Finding 9).
