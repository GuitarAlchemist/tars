# Contract: TARS-IX Artifact Exchange Contracts

- **Status:** Approved
- **Area:** Runtime / Contracts
- **Owner:** TARS V2 & IX Teams
- **Version:** 1.0.0

## Purpose

This contract specifies the structured JSON and JSON-Lines (JSONL) artifact exchange formats between the **TARS V2 Runtime** (the execution engine) and the **IX Algorithm Engine** (the analysis/evaluation engine).

By adhering to these schemas, TARS provides predictable telemetry that IX can ingest using its local DuckDB pipeline layer, ensuring decoupled analytics, scoring, performance tracking, and compliance checks.

---

## 1. Closure Contract (`closure-contract.json`)

The `closure-contract.json` defines the goal, constraints, and operational bounds for a discrete unit of execution (a "closure"). It is generated by the TARS Cortex (or the Semantic-to-Contract pipeline) before execution.

| Field | Type | Description | Required |
| :--- | :--- | :--- | :--- |
| `contract_id` | UUID/String | Globally unique identifier for this contract. | Yes |
| `parent_issue` | String | Reference to the parent GitHub Issue or task (e.g., `GuitarAlchemist/tars#70`). | Yes |
| `goal` | String | High-level natural language description of the objective to achieve. | Yes |
| `schema_version` | String | Contract schema version (must be `1.0.0`). | Yes |
| `timestamp` | ISO8601 String | Date and time when this contract was generated. | Yes |
| `constraints` | Object | Operational limits governing the closure execution (detailed below). | Yes |
| `required_skills` | Array<String> | Set of skill identifiers required for this closure (e.g., `standard.run_command`, `git.commit`). | Yes |
| `invariants` | Array<String> | Absolute logical state rules that must be preserved during execution. | Yes |

### `constraints` Object Schema

| Field | Type | Description | Required |
| :--- | :--- | :--- | :--- |
| `max_duration_seconds` | Integer | Absolute maximum wall-clock runtime allowed. | Yes |
| `budget_tier` | Enum | Allowed cost level: `free-local`, `cloud-low`, `cloud-high`. | Yes |
| `max_llm_calls` | Integer | Limit on the number of individual LLM prompts allowed. | Yes |
| `token_budget` | Integer | Optional max limit on total input/output tokens. | No |

## 2. Closure Run Summary (`closure-run.json`)

The `closure-run.json` represents the execution summary and results of the closure. It is written by the TARS Closure Factory after execution completes.

| Field | Type | Description | Required |
| :--- | :--- | :--- | :--- |
| `run_id` | UUID/String | Unique execution identifier for this specific run. | Yes |
| `contract_id` | UUID/String | Reference identifier of the matching `closure-contract.json`. | Yes |
| `status` | Enum | Final execution outcome: `success`, `failure`, `timeout`, `halted`, `error`. | Yes |
| `duration_ms` | Integer | Total elapsed wall-clock execution time in milliseconds. | Yes |
| `timestamp_start` | ISO8601 String | Time when execution commenced. | Yes |
| `timestamp_end` | ISO8601 String | Time when execution ended. | Yes |
| `llm_call_count` | Integer | Total count of LLM prompts issued. | Yes |
| `tokens_used` | Object | Invoiced token counts (detailed below). | Yes |
| `error` | Object | Execution error details (if `status` is not `success`). | No |
| `output_artifacts` | Array<Object> | List of files written, modified, or registered during execution. | Yes |

### `tokens_used` Object Schema

| Field | Type | Description | Required |
| :--- | :--- | :--- | :--- |
| `prompt_tokens` | Integer | Number of input/prompt tokens consumed. | Yes |
| `completion_tokens` | Integer | Number of output/completion tokens consumed. | Yes |
| `total_tokens` | Integer | Total tokens consumed. | Yes |

### `output_artifacts` Element Schema

| Field | Type | Description | Required |
| :--- | :--- | :--- | :--- |
| `filepath` | String | Path to the generated or modified file relative to workspace root. | Yes |
| `description` | String | Explanation of the artifact's purpose/contents. | Yes |
| `sha256_hash` | String | SHA-256 checksum of the generated file for integrity validation. | Yes |

## 3. Trace Events Stream (`trace-events.jsonl`)

The `trace-events.jsonl` contains line-delimited JSON objects representing the sequential stream of telemetry events during closure execution. It is appended to in real-time.

Each line is a single JSON object containing a common envelope, and an event-specific `payload`.

### Common Envelope Fields

| Field | Type | Description | Required |
| :--- | :--- | :--- | :--- |
| `event_id` | UUID/String | Unique identifier of the specific telemetry event. | Yes |
| `run_id` | UUID/String | Matching closure run identifier. | Yes |
| `timestamp` | ISO8601 String | Event occurrence timestamp. | Yes |
| `event_type` | Enum | The kind of event: `step_start`, `step_end`, `llm_request`, `llm_response`, `tool_call`, `tool_response`, `error`. | Yes |
| `payload` | Object | Specific event-dependent details. | Yes |

### Event Payload Schemas

#### A. `step_start` Payload
*   `step_name`: String. The name/identifier of the execution step in the WoT plan.
*   `cognitive_mode`: Enum. `Exploratory`, `Convergent`, or `Critical`.

#### B. `step_end` Payload
*   `step_name`: String. Matches the starting step.
*   `success`: Boolean. Indication if step completed successfully.
*   `outcome_summary`: String. Summarized output message of the step.

#### C. `llm_request` Payload
*   `provider`: String. The AI model provider used (e.g., `ollama`, `openai`, `anthropic`).
*   `model`: String. Name of the active model.
*   `temperature`: Number. Prompt temperature.
*   `prompt_template_id`: String (optional). ID of the prompt blueprint used.

#### D. `llm_response` Payload
*   `latency_ms`: Integer. Latency of the LLM call.
*   `tokens_prompt`: Integer. Inbound prompt tokens.
*   `tokens_completion`: Integer. Outbound completion tokens.
*   `stop_reason`: String. Reason for completion finish.

#### E. `tool_call` Payload
*   `tool_name`: String. Name of the tool invoked (from `ISkillRegistry`).
*   `arguments`: Object. Key-value arguments passed to the tool.

#### F. `tool_response` Payload
*   `tool_name`: String. Name of the tool invoked.
*   `success`: Boolean. True if tool executed without errors.
*   `response_preview`: String. First 200 characters of tool output (for semantic review).

#### G. `error` Payload
*   `error_type`: String. Exception or error classifier.
*   `message`: String. Human-readable error details.
*   `stack_trace`: String (optional). Stack trace of execution failure.

## 4. IX Scorecard (`ix-scorecard.json`)

The `ix-scorecard.json` represents the semantic and logical evaluation score of a closure run, calculated by the IX Engine from the telemetry traces.

| Field | Type | Description | Required |
| :--- | :--- | :--- | :--- |
| `scorecard_id` | UUID/String | Unique identifier for this scorecard. | Yes |
| `run_id` | UUID/String | Reference to the evaluated `closure-run.json`. | Yes |
| `timestamp` | ISO8601 String | Time when scorecard was computed. | Yes |
| `evaluator_version` | String | Release version of the scoring model/script. | Yes |
| `overall_score` | Number | Normalized aggregate quality score (between `0.0` and `1.0`). | Yes |
| `decision_gate` | Enum | Recommendation: `promote`, `keep_revising`, `escalate`, `reject`. | Yes |
| `metrics` | Object | Detailed semantic metrics scored by the engine (detailed below). | Yes |
| `criteria` | Array<Object> | Exact score breakdown for individual evaluation rules. | Yes |

### `metrics` Object Schema

| Field | Type | Description | Required |
| :--- | :--- | :--- | :--- |
| `semantic_drift` | Number | Score (0.0 - 1.0) indicating distance from contract goal. 0.0 is perfect alignment. | Yes |
| `reasoning_depth` | Number | Score (0.0 - 1.0) assessing cognitive depth (exploratory vs. critical transitions). | Yes |
| `tool_efficiency` | Number | Score (0.0 - 1.0) evaluating unnecessary or redundant tool calls. | Yes |
| `error_density` | Number | Ratio of failed events relative to total trace size. | Yes |

### `criteria` Element Schema

| Field | Type | Description | Required |
| :--- | :--- | :--- | :--- |
| `name` | String | Evaluation rule name (e.g., "goal-alignment", "token-conservation"). | Yes |
| `weight` | Number | Importance weighting of this rule (0.0 - 1.0). | Yes |
| `score` | Number | Score assigned to this criteria (0.0 - 1.0). | Yes |
| `feedback` | String | Qualitative improvement feedback. | Yes |

## 5. IX Analysis Report (`ix-analysis-report.json`)

The `ix-analysis-report.json` is a multi-run analytical artifact compiled by IX's DuckDB engine. It tracks historical trends, performance drift, and system regressions.

| Field | Type | Description | Required |
| :--- | :--- | :--- | :--- |
| `report_id` | UUID/String | Unique identifier for the analysis report. | Yes |
| `scope` | Enum | Analysis scope: `single-run`, `trend-series`, `monthly-digest`. | Yes |
| `timestamp` | ISO8601 String | Timestamp when the report was compiled. | Yes |
| `runs_analyzed` | Array<String> | List of evaluated `run_id`s. | Yes |
| `drift_detected` | Boolean | True if semantic drift or resource usage regression exceeded safety thresholds. | Yes |
| `regressions` | Array<Object> | Details of identified performance or logical regressions. | Yes |
| `insights` | Array<String> | Automated qualitative optimizations extracted from trace mining. | Yes |

### `regressions` Element Schema

| Field | Type | Description | Required |
| :--- | :--- | :--- | :--- |
| `metric` | String | The regressed dimension (e.g., "duration_ms", "token_count"). | Yes |
| `baseline_value` | Number | Historical moving average baseline. | Yes |
| `observed_value` | Number | Value observed in the latest evaluated run. | Yes |
| `percentage_change` | Number | Calculated growth/regression rate. | Yes |
| `severity` | Enum | Impact severity: `low`, `medium`, `high`. | Yes |

## Invariants & Compliance Rules

1.  **Strict Temporal Monotonicity**: Timestamp fields must always flow forward in chronological order: `timestamp_start` <= `timestamp` (any trace event) <= `timestamp_end`.
2.  **No Secret Leaks**: No raw secrets, SSH keys, passwords, or authentication bearer tokens may reside within any exchange artifact. All payloads must be pre-scrubbed.
3.  **Self-Contained References**: A `closure-run.json` must always reference a valid, existing `closure-contract.json` ID.
4.  **Local-First Accessibility**: All formats must be structured so they are easily queryable via standard SQL inside DuckDB (e.g., using `read_json_auto()` or querying Parquet files generated from the trace stream).
